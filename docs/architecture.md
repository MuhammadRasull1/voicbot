# PapaBiz (papa_projects) — описание архитектуры, стека и логики работы

> Статус документа: **концепция / проектирование (v0.1)**. Проект находится на стадии
> архитектурного проектирования, код ещё не написан. Документ фиксирует целевую
> архитектуру, стек, модель данных и бизнес-логику, чтобы по нему можно было
> вести разработку и проверять решения.

Документ подготовлен для загрузки в NotebookLM. Описывает универсальный рабочий
инструмент малого бизнеса «PapaBiz» (репозиторий `papa_projects`) — концепцию,
стек, модель данных, планируемые эндпоинты и бизнес-логику.

---

## 1. Назначение сервиса

PapaBiz — универсальный backend-инструмент для ежедневных операций малого бизнеса
(проект отца). Система закрывает базовый контур работы микробизнеса без привязки к
конкретной отрасли:

- **Каталог** — товары или услуги с ценами, категориями, единицами измерения,
  себестоимостью и остатками на складе.
- **Клиенты** — база клиентов с контактами и историей заказов.
- **Заказы** — создание заказа из каталога, расчёт суммы на сервере, статусная
  машина, автоматическое списание/возврат остатков.
- **Склад** — остатки по товарам, движения (`приход / расход / корректировка / продажа`),
  запрет продажи сверх остатка.
- **Учёт расходов** — простые статьи расходов для расчёта чистой прибыли.
- **Отчёты** — выручка, валовая и чистая прибыль за период, топ товаров, остатки.

Ключевая идея: **одно приложение вместо Excel-таблиц**. Отрасль не фиксирована:
модель «товар/услуга с ценой и остатком» применима к торговле, производству,
услугам, ферме или доставке. Персонализация под конкретный бизнес (названия,
доп. поля) выносится в конфигурацию и каталог, а не в код.

Фронтенда в первой версии нет: сервис — чистый backend, потребляемый по HTTP/JSON;
поверх него позже строится простой веб-интерфейс или Telegram-бот.

## 2. Технологический стек

| Слой      | Технология                                             | Обоснование |
|-----------|--------------------------------------------------------|-------------|
| Runtime   | Node.js 22+ (CommonJS)                                 | встроенный драйвер SQLite без нативных сборок, простота деплоя |
| Фреймворк | Express 5.x                                            | минималистичный, гибкий, огромная экосистема |
| БД        | SQLite через встроенный модуль `node:sqlite` (`DatabaseSync`) | ноль настройки, один файл, транзакции; переносима на PostgreSQL |
| Auth      | JWT (`jsonwebtoken`, HS256) + `bcryptjs` для паролей   | stateless-авторизация, безопасное хеширование |
| Валидация | `zod` (схемы в `src/validators/`)                      | декларативные схемы, единая точка проверки входа |
| Деньги    | целые числа в копейках (`*_cents`)                     | исключение ошибок округления с плавающей точкой |

Планируемые зависимости: `express`, `jsonwebtoken`, `bcryptjs`, `zod`. База —
стандартный драйвер Node.js, поэтому проект не требует компиляции нативных модулей.
Стек повторяет проверенную схему соседнего проекта `lunchistan`, что упрощает
поддержку обоих проектов одним человеком.

## 3. Архитектура

### 3.1 Общая схема

```
HTTP-запрос
    │
    ▼
Express (src/app.js)
    │  express.json() — парсинг JSON-тела
    │  обработчики по префиксам:
    │    /health, /api/auth, /api/products, /api/categories, /api/clients,
    │    /api/orders, /api/stock, /api/expenses, /api/reports
    ▼
Routes (src/routes/*) — тонкие слои HTTP-контракта
    │  middleware цепочки:
    │    requireAuth / requireRole (JWT, RBAC)
    │    validate(schema, source) — zod-валидация
    ▼
Services (src/services/*) — бизнес-логика и SQL
    │  транзакции (tx), списание/возврат остатков,
    │  снапшоты цен, статусная машина заказов, расчёт прибыли
    ▼
db/index.js — хелперы all/get/run/tx поверх node:sqlite
    ▼
SQLite (data/papabiz.db)
```

### 3.2 Принцип слоёв

- **Routes** — описывают HTTP-контракт: метод, путь, middleware, статус ответа.
  Не содержат SQL и не знают о БД.
- **Services** — вся бизнес-логика и SQL. Роуты вызывают методы сервисов и отдают
  результат в `res.json(...)`.
- **Middleware** — сквозные функции: аутентификация, ролевая авторизация, валидация,
  централизованная обработка ошибок.
- **Поток данных строго один:** routes → services → db. Обратных зависимостей нет.
- Многошаговые операции (заказ, отмена, движение склада) выполняются только внутри
  транзакций — частичные изменения невозможны.

## 4. Модель данных

### 4.1 ER-диаграмма (текстовая)

```
users 1───∞ orders (created_by)          кто оформил заказ
users 1───∞ clients (created_by)         кто добавил клиента

clients 1───∞ orders (client_id)         заказы клиента

categories 1───∞ products (category_id)  категория товара/услуги
products 1───∞ order_items (product_id)  позиции заказа (снапшот)
products 1───∞ stock_movements (product_id)  движения склада

orders 1───∞ order_items (order_id)      позиции заказа (снапшот)
orders 1───0..∞ stock_movements (order_id)   списание/возврат по заказу

expenses — автономная таблица учёта расходов
```

### 4.2 Таблицы

**users** — сотрудники системы (владелец и операторы).
`id`, `name`, `email` (UNIQUE), `password_hash`, `role` (CHECK: `owner`|`staff`),
`is_active` (0/1), `created_at`.

**categories** — категории каталога: `id`, `name` (UNIQUE).

**products** — товар или услуга.
`id`, `category_id` → categories (SET NULL), `name`, `description`, `unit`
(например `шт`, `кг`, `усл.`), `price_cents` (CHECK ≥ 0), `cost_cents` (CHECK ≥ 0,
себестоимость для расчёта прибыли), `stock_quantity` (CHECK ≥ 0, остаток),
`sku` (артикул, UNIQUE, nullable), `is_active` (0/1), `created_at`.

**clients** — база клиентов.
`id`, `name`, `phone` (UNIQUE, nullable), `email` (nullable), `note`, `created_at`.

**orders** — заказы.
`id`, `client_id` → clients (SET NULL), `created_by` → users (SET NULL),
`status` (CHECK: `pending`|`confirmed`|`done`|`cancelled`),
`total_cents`, `discount_cents` (CHECK ≥ 0), `note`, `created_at`, `updated_at`.
Оплата по умолчанию фиксируется переходом в `done`; в будущем добавляется поле
`paid_cents` для частичной оплаты.

**order_items** — позиции заказа (исторический снапшот).
`id`, `order_id` → orders (CASCADE), `product_id` → products (SET NULL),
`product_name`, `unit`, `price_cents`, `cost_cents`, `quantity` (CHECK > 0).
Имя, цена и себестоимость копируются в момент заказа, поэтому изменение каталога
позже не искажает историю заказов.

**stock_movements** — движения склада (аудит всех изменений остатков).
`id`, `product_id` → products (CASCADE), `type` (CHECK: `in`|`out`|`adjust`|`sale`),
`quantity` (CHECK ≠ 0; для `sale` — отрицательное при списании), `order_id` →
orders (SET NULL), `note`, `created_at`.

**expenses** — расходы бизнеса.
`id`, `name` (например «аренда», «закупка», «транспорт»), `amount_cents` (CHECK ≥ 0),
`note`, `created_at`. Статья кодируется строкой-списком, отдельной таблицы категорий
расходов в MVP не требуется.

### 4.3 Ключевые проектные решения

- **Деньги — только целые копейки** (`price_cents`, `cost_cents`, `total_cents`,
  `amount_cents`). Никаких `FLOAT/DOUBLE`.
- **Снапшот позиций заказа** — `order_items` фиксирует имя, цену и себестоимость на
  момент заказа; удаление товара из каталога не ломает историю.
- **Склад хранит только остаток**, а вся история изменений — в `stock_movements`.
  Остаток всегда можно пересчитать из движений.
- **Каскады** — удаление заказа каскадит на его позиции; удаление товара обнуляет
  ссылки в `order_items`/`stock_movements`, но строки сохраняются.
- **Индексы** на все FK-колонки (orders.client_id, orders.created_by, order_items.order_id,
  order_items.product_id, stock_movements.product_id, products.category_id).
- **PRAGMA foreign_keys = ON** включается на каждом соединении; WAL-режим журнала.

## 5. Аутентификация и роли (RBAC)

### 5.1 Регистрация и вход

- `POST /api/auth/register` — создаёт пользователя. Пароль хешируется bcrypt (cost 10).
  Роль при регистрации — `staff`; первый пользователь системы назначается `owner`
  (например, через seed или одноразовую переменную окружения `SEED_OWNER`).
- `POST /api/auth/login` — сверка bcrypt, выдача JWT.
- JWT payload: `{ sub: <user_id>, role, name, email }`, подпись HS256, срок 7 дней.

### 5.2 Защита маршрутов

- `requireAuth` — проверяет заголовок `Authorization: Bearer <token>`, кладёт payload в
  `req.user`. Ошибки: `401 UNAUTHORIZED` (нет токена), `401 INVALID_TOKEN` (просрочен/подделан).
- `requireRole('owner')` — ограничение по `req.user.role`. Недостаточно прав → `403 FORBIDDEN`.

### 5.3 Матрица прав

| Действие | staff | owner |
|----------|:-----:|:-----:|
| Просмотр каталога, клиентов, заказов, отчётов | ✓ | ✓ |
| Создание/изменение заказов | ✓ | ✓ |
| Склад: приход, продажа, расход | ✓ | ✓ |
| Склад: корректировка остатка (`adjust`) | ✗ | ✓ |
| Создание/редактирование товаров, категорий, клиентов | ✓ | ✓ |
| Удаление записей (заказ, товар, клиент) | ✗ | ✓ |
| Учёт расходов | ✓ | ✓ |
| Управление пользователями | ✗ | ✓ |
| Отмена заказа с возвратом остатков | ✓ | ✓ |

## 6. Жизненный цикл запроса

1. **Парсинг JSON** — `express.json()` разбирает тело запроса.
2. **Валидация** — middleware `validate(schema, source)` вызывает `schema.safeParse`.
   `source` — `'body'` | `'query'` | `'params'`. При неуспехе → `400 VALIDATION` со списком
   проблем (поле + сообщение). Распарсенные данные кладутся в `req.validated[source]`
   (важно: `req.query` в Express 5 — ленивый геттер, его нельзя перезаписывать).
3. **Аутентификация/авторизация** — при необходимости `requireAuth` / `requireRole`.
4. **Бизнес-логика** — вызов метода сервиса; сервис работает с БД через хелперы
   `db/index.js`. Все многошаговые операции оборачиваются в транзакцию `tx(...)`.
5. **Ответ** — `res.json()` / `res.status(201).json()` / `res.status(204).end()`.
6. **Ошибки** — единый формат (раздел 8), централизованный обработчик.

## 7. Планируемые эндпоинты API

Базовый URL: `http://localhost:3000`. Все тела — JSON. Авторизованные маршруты
требуют заголовок `Authorization: Bearer <token>`.

### 7.1 Сервис

**GET /health** — проверка живости.
```json
{ "status": "ok", "service": "papabiz-api", "env": "development", "time": "..." }
```

### 7.2 Аутентификация — /api/auth

- **POST /api/auth/register** — создание пользователя `{ "name", "email", "password", "role?" }`
  (role по умолчанию `staff`). Ошибки: `400 VALIDATION`, `409 EMAIL_EXISTS`.
- **POST /api/auth/login** — вход `{ "email", "password" }` → `{ "token", "user" }`.
  Ошибка: `401 BAD_CREDENTIALS`.
- **GET /api/auth/me** (auth) — профиль текущего пользователя.

### 7.3 Каталог — /api/products

- **GET /api/products** — список. Query: `category_id`, `search` (LIKE по name/description),
  `is_active=true|false`, `limit` (1–100, по умолч. 50), `offset`.
  Ответ: `{ "items": [...], "total": N }`; строка дополнена `category_name`.
- **GET /api/products/:id** — товар с `category_name`. `404 NOT_FOUND`.
- **POST /api/products** (auth) — создание:
  ```json
  { "name": "Молоко 1 л", "category_id": 1, "unit": "шт", "price_cents": 8990, "cost_cents": 6500, "stock_quantity": 40 }
  ```
  Ответ `201`.
- **PUT /api/products/:id** (auth) — частичное обновление. Изменение `stock_quantity`
  напрямую запрещено — только через `/api/stock/adjust`.
- **DELETE /api/products/:id** (owner) — удаление (снапшоты заказов сохраняются). `204`.

### 7.4 Категории — /api/categories

- **GET /api/categories** — список `{ "items": [...] }`.
- **POST /api/categories** (auth) — создать `{ "name" }`. `409 CATEGORY_EXISTS` при дубликате.

### 7.5 Клиенты — /api/clients

- **GET /api/clients** — список. Query: `search`, `limit`, `offset`.
- **POST /api/clients** — создание `{ "name", "phone?", "email?", "note?" }`.
  `409 CLIENT_EXISTS` при дубликате phone.
- **GET/PUT/DELETE /api/clients/:id** (DELETE — owner) — просмотр с историей заказов,
  обновление, удаление.

### 7.6 Заказы — /api/orders (все маршруты auth)

- **POST /api/orders** — оформить заказ. Запрос:
  ```json
  { "client_id": 1, "items": [ { "product_id": 1, "quantity": 2 } ], "discount_cents": 0, "note": "" }
  ```
  Логика (см. раздел 9.1): пустой список → `400 EMPTY_ORDER`; недоступный/неактивный
  товар → `404 NOT_FOUND`; недостаточно остатка → `409 INSUFFICIENT_STOCK`; иначе в одной
  транзакции создаются заказ и позиции со снапшотом, списываются остатки, пишутся
  движения склада. Ответ `201` — заказ с позициями.
- **GET /api/orders** — список. Фильтры: `status`, `client_id`, даты `from`/`to`;
  пагинация `limit`/`offset`. Строка дополнена `client_name`, `user_name`.
- **GET /api/orders/:id** — заказ с позициями. `404 NOT_FOUND`.
- **PATCH /api/orders/:id/status** — смена статуса `{ "status": "done" }`.
  Отмена (`cancelled`) из статусов `pending`/`confirmed` возвращает остатки
  (раздел 9.2). Недопустимый переход → `409 INVALID_TRANSITION`.
- **DELETE /api/orders/:id** (owner) — удаление только `pending`/`cancelled`.
  Иначе → `409 CONFLICT`. `204`.

### 7.7 Склад — /api/stock (все маршруты auth)

- **POST /api/stock/in** — приход `{ "product_id", "quantity", "note?" }` (quantity 1–99999).
  Ответ `201` — движение.
- **POST /api/stock/out** — расход по не-заказной причине `{ "product_id", "quantity", "note?" }`.
  Недостаточно остатка → `409 INSUFFICIENT_STOCK`.
- **POST /api/stock/adjust** (owner) — корректировка `{ "product_id", "new_stock_quantity" }`
  (CHECK ≥ 0). Пишется движение типа `adjust` с разницей.
- **GET /api/stock/movements** — журнал движений. Фильтры: `product_id`, `type`, даты, пагинация.
- **GET /api/stock** — текущие остатки (дельта между приходом и расходом).

### 7.8 Расходы — /api/expenses

- **GET /api/expenses** — список. Фильтры по датам, пагинация.
- **POST /api/expenses** — создать `{ "name", "amount_cents", "note?" }`. Ответ `201`.
- **DELETE /api/expenses/:id** (owner) — удалить. `204`.

### 7.9 Отчёты — /api/reports (все маршруты auth)

- **GET /api/reports/summary?from&to** — сводка за период:
  ```json
  {
    "revenue_cents": 125000,
    "gross_profit_cents": 42300,
    "expenses_cents": 18500,
    "net_profit_cents": 23800,
    "orders_count": 14,
    "top_products": [ { "product_name": "...", "quantity": 30, "revenue_cents": 60000 } ]
  }
  ```
- **GET /api/reports/stock** — отчёт по остаткам: текущий остаток и сумма по себестоимости.

## 8. Формат ошибок

Все ошибки возвращаются в едином конверте:

```json
{
  "error": {
    "code": "VALIDATION",
    "message": "Некорректные входные данные",
    "details": [ { "path": "email", "message": "Некорректный email" } ]
  }
}
```

`details` присутствует только у `400 VALIDATION`. Матрица кодов:

| HTTP | Код | Условие |
|------|-----|---------|
| 400 | `VALIDATION` | zod-валидация не прошла |
| 400 | `EMPTY_ORDER` | заказ без позиций |
| 401 | `UNAUTHORIZED` | нет Bearer-токена |
| 401 | `INVALID_TOKEN` | токен недействителен/истёк |
| 401 | `BAD_CREDENTIALS` | неверный email/пароль |
| 403 | `FORBIDDEN` | недостаточно прав |
| 404 | `NOT_FOUND` | ресурс не найден / неактивен |
| 409 | `CONFLICT` | нарушение целостности (SQLite constraint) |
| 409 | `EMAIL_EXISTS` | email уже занят |
| 409 | `CATEGORY_EXISTS` | категория уже существует |
| 409 | `CLIENT_EXISTS` | клиент с таким телефоном уже есть |
| 409 | `INSUFFICIENT_STOCK` | недостаточно остатка на складе |
| 409 | `INVALID_TRANSITION` | запрещённый переход статуса заказа |
| 500 | `INTERNAL` | непредвиденная ошибка (лог в консоли) |

`ApiError` (класс в `middleware/errorHandler.js`) — конструктор `(status, code, message, details?)`.
Неизвестные маршруты → `404 NOT_FOUND` через `notFoundHandler`.

## 9. Бизнес-логика

### 9.1 Оформление заказа (orders.service.js, `create`)

Шаги в одной транзакции:
1. Валидация позиций: каждый `product_id` существует и активен; неактивный/удалённый
   товар → `404 NOT_FOUND`.
2. Проверка остатков: для каждой позиции `products.stock_quantity ≥ quantity`;
   иначе → `409 INSUFFICIENT_STOCK` с перечислением недостающих товаров.
3. Сумма считается на сервере: `total = Σ price_cents × quantity − discount_cents`
   (клиент сумму не передаёт). `discount_cents ≤ total` (иначе → `400 VALIDATION`).
4. Создаётся `orders` (status=`pending`), на каждую позицию — `order_items`
   со **снапшотом** `product_name`, `unit`, `price_cents`, `cost_cents`.
5. Для каждого товара: `stock_quantity -= quantity`, пишется `stock_movements`
   типа `sale` (quantity отрицательное, `order_id` заполнен).
6. Всё коммитится; при ошибке на любом шаге — полный откат.

### 9.2 Отмена заказа (возврат остатков)

- Отмена разрешена из статусов `pending` и `confirmed` (см. статусную машину).
- В транзакции: статус → `cancelled`, по каждой позиции `stock_quantity += quantity`,
  пишется движение `sale` с положительным quantity и пометкой `note = "возврат по заказу #<id>"`.
- Удалённые позиции (товар удалён из каталога) пропускаются, их остатки не возвращаются —
  проверка по `product_id IS NOT NULL`.

### 9.3 Статусная машина заказа

```
pending ──► confirmed ──► done
   │            │
   └──────► cancelled ◄──┘
```

| Из | В | Эффект на склад |
|----|---|-----------------|
| `pending` | `confirmed` | нет |
| `pending` | `cancelled` | возврат остатков |
| `confirmed` | `done` | нет (списание было при создании) |
| `confirmed` | `cancelled` | возврат остатков |
| `done` | — | — |
| `cancelled` | — | — |

Повторная установка того же статуса — no-op (успех). Любой другой переход →
`409 INVALID_TRANSITION` с сообщением о разрешённых вариантах. Удалить можно только
заказ в `pending` или `cancelled`.

> **Решение по умолчанию:** списание остатков происходит при создании заказа
> (`pending`), а не при подтверждении. Это резервирует товар. Если для бизнеса
> отца нужен другой порядок (списание при `confirmed`/`done`), поведение меняется
> в одном месте — в `orders.service.js`, статусная машина остаётся прежней.

### 9.4 Деньги и расчёт прибыли

- Единственный источник цены и себестоимости — `products` на момент заказа;
  далее они живут в снапшоте `order_items`.
- **Валовая прибыль** = `Σ (price_cents − cost_cents) × quantity` по заказам в статусах
  `confirmed`/`done` за период.
- **Чистая прибыль** = валовая прибыль − `Σ expenses.amount_cents` за период.
- Отчёты агрегируют только заказы в `confirmed`/`done` — `pending` и `cancelled`
  исключаются из выручки.

### 9.5 Склад и движения

- Единственный способ изменить остаток — движение `stock_movements`; прямой UPDATE
  `products.stock_quantity` из роута запрещён.
- Типы движений: `in` (приход), `out` (не-заказной расход), `adjust` (корректировка
  владельцем), `sale` (списание по заказу / возврат).
- Негативные остатки исключаются CHECK-ограничением `stock_quantity ≥ 0` и проверкой
  в сервисе перед списанием.

### 9.6 Валидация входных данных

- Схемы в `src/validators/index.js`. Обязательные поля: `name`/`email`/`password` при
  регистрации, `name` и `price_cents` при создании товара, `name` и `amount_cents` для
  расходов, `client_id` и `items` для заказа.
- Числа в query/params приводятся через `z.coerce` (`id`, `limit`, `offset`, `product_id`...).
- Лишние поля схемы отбрасываются (strip по умолчанию у zod) — это защищает сервис от
  инъекций непредусмотренных полей.
- Пагинация: `limit` 1–100 (default 50), `offset` ≥ 0 (default 0).
- `quantity` в заказе и движениях — целые 1–99999.

### 9.7 Безопасность

- Пароли никогда не хранятся в открытом виде: bcrypt (cost 10).
- Деньги — целые копейки, нет проблем float-арифметики.
- SQL — только параметризованные запросы (препейрд-стейтменты `node:sqlite`),
  пользовательский ввод никогда не конкатенируется в SQL.
- Табличные CHECK-ограничения (роли, статусы, неотрицательность цен/остатков) страхуют
  данные на уровне БД.
- Чувствительные операции (удаление, корректировка склада, управление пользователями)
  доступны только `owner`.

## 12. Ограничения и направления развития

- **Хранение в файле** — SQLite подходит для одного инстанса; при росте — переход на
  PostgreSQL (схема переносима, типы простые).
- **Нет интеграции оплаты** — оплата фиксируется статусом, без платёжного шлюза.
- **Нет уведомлений** — смены статусов не рассылаются (клиент видит при звонке).
- **Один склад** — модель без нескольких точек/складов; при необходимости — добавление
  `warehouse_id` в `products` и `stock_movements`.
- **Пагинация** — простые LIMIT/OFFSET, без курсоров.
- **Логирование** — только консоль, без структурированных логов/трейсинга.
- **Интерфейс** — фронтенд не входит в MVP; следующий шаг — простой UI или Telegram-бот.

## Приложение. Контракт концепции (сводно)

- Сервис: **PapaBiz** (репозиторий `papa_projects`), чистый REST API без фронтенда.
- Отрасль: универсальная; каталог настраивается, код от отрасли не зависит.
- Стек: Node.js 22+ (CommonJS), Express 5, SQLite (`node:sqlite`), JWT, bcryptjs, zod.
- Деньги — целые копейки; остатки — целые единицы.
- Слои: routes (тонкие) → services (толстые) → db-хелперы; многошаговые операции — в транзакциях.
- Позиции заказов — снапшоты имени, цены и себестоимости.
- Списание остатков — при создании заказа; возврат — при отмене.
- В отчёты попадают только `confirmed`/`done` заказы.
- Роли: `owner` (полный доступ) и `staff` (операционные операции).
